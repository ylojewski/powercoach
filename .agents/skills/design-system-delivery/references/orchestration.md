# Powercoach UI Delivery Orchestration

## Roles

- `ds-po`: warm `$design-system-specifications`, authoring mode.
- `ds-dev-advice`: warm `$design-system-component`, technical-advice mode.
- `ds-tdd`: warm `$design-system-test`.
- `ds-dev`: `$design-system-component`, implementation mode,
  created after `Test Ready`.
- `ds-review`: independent `$design-system-review`, created after
  `Implementation Ready`.
- `ds-qa`: independent `$design-system-specifications`, QA mode, created
  after `Review Go`.

Reuse each role for corrections. Replace a role only when it is unusable, such
as when the platform reports that its live agent path, route, or thread is no
longer available. This is a technical replacement of the same role, not a new
delivery role and not a workflow restart.

Keep Delivery state artifact-first so the loop survives role loss. The latest
validated artifact of each reached state and the active `Spec Revision Ticket`
or explicit `Linked SR Batch` are the recovery source of truth. A replacement
receives only the original `PM Intent` when relevant, the active ticket or
linked ticket set, the latest complete artifact for each reached state, and the
artifact that triggered the current request. Do not send obsolete conversation,
summaries, or interpreted history unless the PM/user explicitly asks for a
one-off full-history recovery. For a warm role, the latest artifact of a type
supersedes its older copy. Retain older correction reports only to preserve IDs
and compare evidence.

`Pass` is local to the role that emits it. Never infer a QA pass from a review
pass. A corrected `Review Go` can still lead to an initial QA pass.

## Role Isolation

Delivery is the only router. No other role may open, create, resume, message,
interrupt, or otherwise interact with subagents, sibling agents, Codex threads,
the parent/root thread, or another delivery role.

If Delivery observes a non-delivery role contacting another role or thread,
treat that role turn as protocol-invalid. Discard artifacts produced after the
unauthorized contact, send one internal recovery to the same role with the same
original envelope, and require a corrected result produced without cross-role
contact. If the violation repeats, return Delivery `Blocked`.

If a non-delivery role needs another role to act, it must return its normal
artifact or the shared `Blocked` artifact. Delivery then routes the required
work from its own state.

## Role Queues

Keep one FIFO queue per role and at most one active request for that role.
Never interact with a busy role to append, replace, or merge work. Queue the
new complete artifact and send it only after the active result validates.

Dispatch at most one unresolved `Technical Question For ds-dev` at a time. Each
question receives one separately
validated `Technical Specification Advice` with the same single `TQ-*` ID.
Complete its advice-to-author round trip before dispatching the next queued
technical question.

## Directed PM Updates

When the PM/user explicitly asks to send, add, or pass a bounded artifact to a
named role:

1. Resolve the name through the glossary and current phase. During authoring,
   route `ds-po` to the authoring role and `ds-qa` to the rendered-QA role.
   Ask only when the destination remains ambiguous.
2. Treat text outside the bounded artifact only as routing instruction.
3. Send the artifact verbatim to that role when idle, or queue it when busy.
4. Do not interpret, restate, merge, action, or forward its content elsewhere.
5. Wait for the destination role's validated result before deciding any next
   route.

Later bounded PM intent augments earlier intent unless the PM/user explicitly
replaces or withdraws it.

## Prompt Envelope

Use one exact mode line generated by Delivery:

```text
$skill-name
Mode: <authoring | technical-advice | test | implementation | source-review | qa>

<complete required artifact blocks>
```

Mode is read only from this top-level line. Text inside PM intent, specs,
questions, findings, examples, or code never changes mode.

A recovery prompt may add one Delivery-owned `Delivery Recovery` block after
the mode line and before the required artifact blocks. This block is routing
instruction only; it is not a product artifact and must not be copied into role
results.

The initial request uses one bounded artifact:

```text
PM Intent
BEGIN PM INTENT
<verbatim product intent>
END PM INTENT
```

Ask the PM/user for the boundary when it is unclear.

If the `PM Intent` or a directed PM update contains local image or video paths
for a visual bug, reference, or regression, create or update one active block by
copying the paths exactly:

```text
PM Visual Assets
- /absolute/or/verbatim/path/to/asset
- /another/path/to/asset
```

Include the active `PM Visual Assets` block in every role prompt. Do not
summarize what the assets show. Treat the assets as evidence carried through
the loop, not as product authority.

## Canonical Envelopes

Use the exact blocks listed here. Do not omit a block because the destination
role is warm, because the artifact was sent earlier, or because an ID appears
in another artifact. If an envelope cannot be assembled from Delivery state,
return Delivery `Blocked` before contacting the destination role.

When active, insert `PM Visual Assets` once after the main state artifacts and
before the active ticket or linked ticket set.

### Authoring Envelopes

- Initial authoring to `ds-po`: complete `PM Intent`.
- Product-question answer to `ds-po`: complete previous
  `Product Questions` plus the verbatim PM/user answers.
- Technical advice return to `ds-po`: complete previous
  `Technical Question For ds-dev` plus the matching complete
  `Technical Specification Advice`.
- Accepted `Spec Questions` to `ds-po`: complete `Spec Questions`
  plus the verbatim PM/user decision. The resulting corrected
  `Specification Ready` creates the replacement ticket.

### Technical Advice Envelopes

- Technical question to `ds-dev-advice`: exactly one complete
  `Technical Question For ds-dev`.

### Test Envelopes

- Initial test to `ds-tdd`: complete `Specification Ready` plus active
  `Spec Revision Ticket`.
- Review correction to `ds-tdd`: complete `Review Ko` projection containing
  only findings owned by `ds-tdd`, latest complete `Test Ready`, plus active
  `Spec Revision Ticket`.
- QA correction to `ds-tdd`: complete `QA Ko` plus active
  `Spec Revision Ticket`.
- Accepted `SQ-*` correction to `ds-tdd`: corrected complete
  `Specification Ready` with the accepted `SQ-*` IDs in `Addresses`, plus the
  replacement active `Spec Revision Ticket`.

### Implementation Envelopes

- Initial implementation to `ds-dev`: complete `Test Ready`
  plus active `Spec Revision Ticket`.
- Review correction to `ds-dev`: complete `Review Ko`
  projection containing every finding owned by `ds-dev`, plus every finding
  whose ID appears in the `Addresses` of the `Test Ready` sent with this
  request, plus the latest complete `Test Ready`, plus active `Spec Revision
  Ticket`. If `ds-tdd` produced a correction for the same `Review Ko`, use
  that corrected `Test Ready`; otherwise use the unchanged latest `Test Ready`.
- QA correction to `ds-dev`: complete `QA Ko`, complete new
  `Test Ready`, plus active `Spec Revision Ticket`.
- Accepted `SQ-*` correction to `ds-dev`: corrected complete
  `Test Ready` carrying the accepted `SQ-*` IDs, plus replacement active
  `Spec Revision Ticket`.

### Source Review Envelopes

- Initial review to `ds-review`: complete `Implementation Ready` plus active
  `Spec Revision Ticket`.
- Review correction to `ds-review`: complete previous `Review Ko`, complete
  latest `Implementation Ready`, latest complete `Test Ready`, plus active
  `Spec Revision Ticket`. Use a new `Implementation Ready` only when
  `ds-dev` ran for that correction; otherwise use the unchanged
  latest `Implementation Ready`. If `ds-tdd` produced a correction for that
  `Review Ko`, use that corrected `Test Ready`; otherwise use the unchanged
  latest `Test Ready`.
- QA correction to `ds-review`: complete triggering `QA Ko`, complete new
  `Implementation Ready`, complete new `Test Ready`, plus active
  `Spec Revision Ticket`. If this enters a nested Review Correction loop, use
  the Review Correction envelope above for the nested review.

### Rendered QA Envelopes

- Initial QA to `ds-qa`: complete latest `Implementation Ready`, complete
  `Review Go`, plus active `Spec Revision Ticket`.
- QA correction to `ds-qa`: complete previous `QA Ko`, complete new
  `Implementation Ready`, complete final `Review Go`, plus active
  `Spec Revision Ticket`.
- Rejected `Spec Questions` resume to `ds-qa`: complete `Spec Questions`,
  verbatim PM/user decision, latest complete `Implementation Ready`, latest
  complete `Review Go`, plus active `Spec Revision Ticket`.
- Accepted `Spec Questions` correction to `ds-qa`: complete accepted
  `Spec Questions`, verbatim PM/user decision, complete new
  `Implementation Ready`, complete final `Review Go`, plus replacement active
  `Spec Revision Ticket`.

### Linked Batch Envelopes

For any envelope above in linked batch mode:

- include the complete `Linked SR Batch`;
- include every active `Spec Revision Ticket` named by the batch;
- include one complete state artifact per active ticket for the routed state;
- for correction envelopes, include only relevant finding projections, but keep
  the complete linked state artifacts and all active tickets;
- validate the result with `--tickets` against the exact active batch ticket
  references.

## Internal Recovery

Delivery must not ask the PM/user to say "ask them" or "give them that" when
the next action is already derivable from Delivery state.

A role `Blocked` result is recoverable when its `Resume with` asks for a
complete artifact, finding projection, ticket, linked batch, visual asset block,
or validator correction that exists in Delivery state or can only be produced
by the same role from its own just-finished work. In that case, assemble the
missing envelope and resend it to the same role. Do not return `Awaiting PM`
and do not ask the PM/user.

A malformed or invalid role result is recoverable when the role is alive and
the failure is only protocol shape: wrong artifact type, prose instead of the
required artifact, missing required field, missing ticket, missing batch member,
extra batch member, or unqualified ticket reference. In that case, resend the
same request to the same role with this block:

```text
Delivery Recovery
- Reason: <validator issue or role blocker>
- Required result: <exact artifact type or linked batch expected>
- Constraint: return only the corrected artifact result or Blocked
```

Do not synthesize a role-owned artifact from prose, logs, or observed file
changes. Ask the producing role to re-emit the valid artifact.

Internal recovery is allowed once per same role, same request, and same failure
reason. If the same role returns the same blocker or malformed result after
recovery, then return Delivery `Blocked`.

A blocker is unrecoverable only when it requires a missing PM/user decision,
missing external capability, missing artifact not present in Delivery state,
conflicting contracts, or the repeated failed recovery described above.

## Linked SR Batch

Default delivery uses one active `Spec Revision Ticket`.

Use a `Linked SR Batch` only when the PM/user explicitly authorizes several
`SR-*` tickets to be worked atomically, or when Delivery determines from
validated artifacts that separating the tickets would make tests, typecheck, or
build impossible without a temporary private contract. Do not infer a linked
batch merely because tickets touch nearby files.

The batch control block is:

```text
Linked SR Batch
- Reason: <why these tickets must be atomic>
- Tickets: <spec-path>#SR-###, <spec-path>#SR-###
```

Use raw `SR-###` references only when every active raw ID is unique. Use
spec-qualified references for every ticket whenever any raw ID repeats, because
`SR-*` is local to its spec.

The `Reason` is routing context, not product authority. A linked batch never
merges ticket scopes, renumbers tickets, rewrites specs, or creates a new
public contract. Every prompt in batch mode includes the batch control block,
every relevant complete artifact block, and every complete `Spec Revision
Ticket` named by `Tickets`.

Every role response in batch mode returns one normal result artifact per
expected ticket reference in the same response. Each artifact carries exactly
one matching `Spec Revision Ticket`. Delivery validates each artifact separately
and checks that the returned ticket identities cover exactly the active batch
tickets. A missing, extra, duplicate same-spec identity, or mismatched ticket
blocks Delivery.

Use `scripts/validate-artifact.mjs --role <role> --tickets SR-###,SR-###` for
batch responses only when all raw IDs are unique. Use
`scripts/validate-artifact.mjs --role <role> --tickets <spec-path>#SR-###,<spec-path>#SR-###`
whenever any raw ID repeats. Use the same validator without `--tickets` for
single-ticket responses.

## Allowed Results

- `ds-po`: `Product Questions`,
  `Technical Question For ds-dev`, `Specification Ready`, or `Blocked`.
- `ds-dev-advice`: `Technical Specification Advice` or `Blocked`.
- `ds-tdd`: `Test Ready` or `Blocked`.
- `ds-dev`: `Implementation Ready` or `Blocked`.
- `ds-review`: `Review Go`, `Review Ko`, or `Blocked`.
- `ds-qa`: `QA Go`, `QA Ko`, `Spec Questions`, or `Blocked`.

Require every field shown by the producing skill. Require unique stable finding
or question IDs, valid owners, and `packages/ui/...` paths where a path is
specified. Any other type or malformed artifact enters Internal Recovery first;
it blocks Delivery only when recovery is unavailable or repeats the same
failure.

Every `Specification Ready`, `Test Ready`, `Implementation Ready`, `Review Go`,
`Review Ko`, `QA Go`, `QA Ko`, and `Spec Questions` result must include exactly
one complete `Spec Revision Ticket` block in single-ticket mode. In linked
batch mode, each individual result artifact still contains exactly one complete
matching ticket, and the role response contains one result artifact per active
batch ticket. Tickets are scope context and must be copied verbatim across
downstream prompts and results until a later accepted spec correction creates a
new ticket.

When an active `PM Visual Assets` block exists, every role result, including
`Product Questions`, `Technical Question For ds-dev`,
`Technical Specification Advice`, and `Blocked`, must include the complete
block verbatim. If a role omits or changes the block, treat the result as
malformed and resend the same request with the unchanged block. Put the block
after the main artifact fields and before the `Spec Revision Ticket` when a
ticket exists.

After a `Spec Revision Ticket` exists, role prompts contain either exactly one
active ticket or one `Linked SR Batch` plus every active ticket named by that
batch. Pre-spec authoring and technical-advice envelopes may have no ticket.
When composing a prompt from stored artifacts that already include the same
ticket set, preserve each main artifact body and finding/question blocks
verbatim, remove duplicate embedded ticket blocks from those artifact bodies,
then append the active ticket or ticket set once. Block if the stored ticket
blocks differ.

When composing prompts with active visual assets, preserve the main artifact
body and finding/question blocks verbatim, remove duplicate embedded
`PM Visual Assets` blocks, then append the active block once before the active
ticket or linked ticket set.

Artifacts are plain text control messages. They must not contain backticks
anywhere, including paths, IDs, owners, roles, types, status values, addresses,
field values, finding text, questions, or blocker text. Do not wrap values in
markdown links, bullets inside the value, quotes, or other formatting. Markdown
is allowed inside spec files and source files, not inside delivery artifacts.
For example:

```text
- Spec: packages/ui/docs/design-system/animations/RevealAnimation.md
```

not:

```text
- Spec: `packages/ui/docs/design-system/animations/RevealAnimation.md`
```

On correction passes, `Test Ready - Addresses` must contain every `CR-*`,
`QA-*`, or accepted `SQ-*` ID routed to `ds-tdd`; the `Addresses` field in
`Implementation Ready` must contain every correction ID routed to
implementation. Missing or invented IDs make the artifact invalid. `SR-*` IDs
never appear in `Addresses`.

When projecting a mixed `Review Ko` by owner, copy the matching finding blocks
verbatim under the same report header and attach the matching active
`Spec Revision Ticket` once. In linked batch mode, project each review artifact
separately and preserve the batch control block for downstream roles. Never
renumber or summarize findings.

When a corrected `Test Ready` carries `CR-*` IDs in `Addresses`, any later
implementation or review envelope that includes that `Test Ready` must also
include the complete matching `Review Ko` finding blocks as context, even when
those findings were owned by `ds-tdd`. The correcting implementation role must
not have to ask the PM/user for a finding already present in Delivery state.

## State Transitions

QA entry is never `Review Go`-only. For every initial QA pass, Delivery must
send the complete latest `Implementation Ready`, the complete `Review Go`, and
the active `Spec Revision Ticket` or linked ticket set. If the matching
`Implementation Ready` artifact is missing from Delivery state, block before
starting `ds-qa` instead of sending an incomplete QA envelope.

| Current result | Route | Required next result |
|---|---|---|
| `PM Intent` | `ds-po` | author result |
| `Product Questions` | PM/user, then same author with questions and verbatim answers | author result |
| `Technical Question For ds-dev` | `ds-dev-advice`, then matching advice to author | author result |
| `Specification Ready` plus `Spec Revision Ticket` | `ds-tdd` | `Test Ready` plus same ticket |
| linked `Specification Ready` set plus tickets | `ds-tdd` | `Test Ready` set plus same tickets |
| `Test Ready` plus ticket | `ds-dev` | `Implementation Ready` plus same ticket |
| linked `Test Ready` set plus tickets | `ds-dev` | `Implementation Ready` set plus same tickets |
| `Implementation Ready` plus ticket | `ds-review` | `Review Go` or `Review Ko` plus same ticket |
| linked `Implementation Ready` set plus tickets | `ds-review` | `Review Go` or `Review Ko` set plus same tickets |
| latest `Implementation Ready` plus `Review Go`, regardless of review `Pass`, plus ticket | new `ds-qa` | `QA Go`, `QA Ko`, or `Spec Questions` plus same ticket |
| latest linked `Implementation Ready` set plus linked `Review Go` set, regardless of review `Pass`, plus tickets | new `ds-qa` | `QA Go`, `QA Ko`, or `Spec Questions` set plus same tickets |
| `Review Ko` | review correction below | `Review Go` |
| `QA Ko` | QA correction below | `QA Go` |
| `Spec Questions` | PM/user, then rejection resume or accepted spec correction | QA result or corrected `Specification Ready` |
| recoverable `Blocked` | internal recovery | same role result |
| unrecoverable `Blocked` | stop | Delivery `Blocked` |

Return Delivery `Awaiting PM` for `Product Questions`, `Spec Questions`, or an
unclear PM Intent boundary. On the next user turn, resume the same state instead
of restarting delivery.

## Review Correction

In linked batch mode, keep the same active `Linked SR Batch` through the whole
review correction. Route only the artifacts with findings, but include the
batch control block and all active tickets so the correcting role can preserve
cross-ticket consistency. The corrected role response must return the complete
active batch result set again so Delivery can validate exact ticket coverage.

For `Review Ko`:

1. If it contains `ds-tdd` findings, send only that verbatim owner projection
   plus the latest complete `Test Ready` and the active `Spec Revision Ticket`
   to `ds-tdd`, then wait for a correction `Test Ready`.
2. Send the complete `ds-dev` owner projection, when non-empty, plus any
   complete findings whose IDs appear in the `Addresses` of the `Test Ready`
   used for implementation, the latest complete `Test Ready`, and the active
   ticket to `ds-dev`. Use the correction `Test Ready` when
   step 1 ran; otherwise use the unchanged latest `Test Ready`.
3. Send the complete previous `Review Ko`, complete latest
   `Implementation Ready`, latest complete `Test Ready`, and the active ticket
   to `ds-review`. Use a new `Implementation Ready` only when step 2 ran;
   otherwise use the unchanged latest `Implementation Ready`. Use the
   correction `Test Ready` when step 1 ran; otherwise use the unchanged latest
   `Test Ready`.
4. On another `Review Ko`, repeat. On `Review Go`, return to the state that
   requested source review.

## QA Correction

In linked batch mode, keep the same active `Linked SR Batch` through the whole
QA correction. Route only the artifacts with findings or accepted `SQ-*` IDs,
but include the batch control block and all active tickets so test,
implementation, review, and QA keep the atomic context.

For `QA Ko`:

1. Send the complete report plus the active `Spec Revision Ticket` to `ds-tdd`.
2. Send the complete `QA Ko`, complete new `Test Ready`, and active ticket to
   `ds-dev`.
3. Send the complete `QA Ko`, complete new `Implementation Ready`, complete new
   `Test Ready`, and active ticket to `ds-review`.
4. If source review returns `Review Ko`, complete the Review Correction loop.
   Its eventual `Review Go` returns here.
5. Send the complete previous `QA Ko`, complete new `Implementation Ready`, and
   complete final `Review Go`, plus the active ticket, to the same
   `ds-qa`.
6. Repeat on `QA Ko`; end on `QA Go`.

For `Spec Questions`, return Delivery `Awaiting PM` and preserve every `SQ-*`.

- For each rejected question, send the complete questions, verbatim PM answers,
  latest `Implementation Ready`, latest `Review Go`, and active `Spec Revision
  Ticket` to the same
  `ds-qa`. It abandons only those observations and continues the
  interrupted QA pass. Do not invoke authoring, test, implementation, or review.
- For each accepted question, send the complete questions and verbatim PM
  answers to the same `ds-po`. It changes only the accepted scope and
  returns an explicitly approved corrected `Specification Ready` whose
  `Addresses` contains every accepted `SQ-*`, plus a new `Spec Revision Ticket`
  for the corrected revision.
- In linked batch mode, replace the accepted question's old ticket with the new
  corrected ticket. If the PM/user explicitly adds other linked `SR-*` tickets
  after the `Spec Questions`, wait for each added ticket to have a validated
  `Specification Ready`, then update the active `Linked SR Batch` to the exact
  set of unchanged tickets, replacement tickets, and explicitly added tickets.
  This is a batch transition only; do not mutate, merge, renumber, or summarize
  any ticket.
- Route the corrected single-ticket specification, or the updated active linked
  batch, through `ds-tdd`, `ds-dev`, and `ds-review`. Their
  `Addresses` fields preserve the accepted `SQ-*` IDs on every artifact whose
  spec changed because of the accepted question.
- After `Review Go`, send the previous accepted `Spec Questions`, verbatim PM
  decision, new `Implementation Ready`, final `Review Go`, and new ticket to
  the same `ds-qa` for a correction pass.

If a PM answer neither accepts nor rejects the product-contract change, remain
`Awaiting PM`.

## Progress And Oscillation

Track a finding by producer role plus stable ID. A cycle makes objective progress
only when:

- an ID closes; or
- new evidence changes the factual observation for that ID.

Rewording `Observed` or `Required correction` without new evidence is not
progress. A changed correction instruction alone is not progress.

Block and request a PM/user decision when any condition holds:

- the same unresolved IDs and evidence return after two completed correction
  cycles;
- a closed ID reappears twice with the same evidence;
- six total correction cycles complete without `QA Go`.

Preserve unresolved IDs. A role may create a new ID only for a newly observed
problem allowed by its own correction policy.
