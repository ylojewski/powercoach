# CardPicker — Q&A

## Q1 - Q&A avec ds-dev en mode pm-advice

Comment tu appellerais un nouveau composant avec des cards sélectionnables, une à la fois (comportement radio), avec une zone Hint pour des informations contextuelles sur la card sélectionnée. La layout peut être à la fois les card stackées verticalement et le Hint en dessous, ou le Hint à gauche et les cards inline à droite, ou l'inverse

## A1

Je l’appellerais **`CardPicker`**.

Le nom décrit l’intention utilisateur — choisir une Card — sans figer la disposition ni exposer l’implémentation radio. Il évite aussi la collision avec `Card.Selector`, qui existe déjà.

Je conserverais les composants actuels comme fondations :

- `Card.Group` et `Card.Selector` portent la sélection radio exclusive.
- `Hint` affiche l’information liée à la valeur sélectionnée.
- `CardPicker` orchestre leur composition et leur disposition.

Pour la disposition, un vocabulaire indépendant du sens d’écriture serait cohérent : `hintPlacement="block-end" | "inline-start" | "inline-end"`.

Alternatives possibles :

- `CardChoiceGroup` : plus explicite comme contrôle de formulaire, mais plus lourd.
- `ChoicePanel` : préférable seulement si la zone contextuelle devient un véritable panneau de contenu, au-delà d’un `Hint`.
- `CardPickerLayout` : si le composant ne gère absolument aucun état et ne fait que placer `Card.Group` et `Hint`.

J’éviterais `CardSelector` à cause de `Card.Selector`, ainsi que `SelectableGrid`, car le composant n’est pas nécessairement une grille.

## Q2

Partons sur CardPicker, je veux aussi un block-start, pas fan de hintPlacement, je préfère placement ou layout (on a déjà un placement dans card donc à voir si c'est la même sémantique), à ajuster stp. Comment tu vois l'api de ce cardpicker, on doit pouvoir avoir une liste de cards et des hints pour chacune d'elle, ainsi qu'un waitingcontent pour inciter le user à faire son choix

## A2

Je partirais sur **`placement`**, pas `layout`.

```ts
type CardPickerPlacement =
  | 'block-start'
  | 'block-end'
  | 'inline-start'
  | 'inline-end'
```

`Card.Visual.placement` décrit déjà le placement de sa région visuelle (`flow | overlay`). Ici, la prop garde la même idée générale — positionner une région interne — mais avec des valeurs logiques relatives au Hint. Il n’y a donc pas de conflit. `layout` serait plus adapté si l’on ajoutait plus tard des variantes comme `grid`, `compact` ou `carousel`.

### Anatomie proposée

Je ferais de `CardPicker` une famille en trois parties :

- `CardPicker.Root` : état de sélection et disposition générale.
- `CardPicker.Group` : compose `Card.Group` et contient les Cards.
- `CardPicker.Hint` : compose `Hint` et associe chaque contenu à une valeur.

```tsx
const [method, setMethod] = useState<'scratch' | 'template' | null>(null)

<CardPicker.Root
  placement="block-end"
  value={method}
  onValueChange={(value) => setMethod(value)}
>
  <CardPicker.Group aria-label="Méthode de création">
    <Card.Root>
      <Card.Selector value="scratch" aria-label="Partir de zéro" />
      <Card.Surface>{/* ... */}</Card.Surface>
    </Card.Root>

    <Card.Root>
      <Card.Selector value="template" aria-label="Utiliser un modèle" />
      <Card.Surface>{/* ... */}</Card.Surface>
    </Card.Root>
  </CardPicker.Group>

  <CardPicker.Hint
    waitingContent="Choisissez une méthode pour afficher plus d’informations."
    hints={[
      {
        value: 'scratch',
        content: 'Créez librement tous les paramètres de votre exercice.'
      },
      {
        value: 'template',
        content: 'Commencez avec une structure déjà configurée.'
      }
    ]}
  />
</CardPicker.Root>
```

### Contrat d’état

`CardPicker.Root` reprendrait le vocabulaire de `Card.Group` :

```ts
interface CardPickerRootProps<TValue> {
  value?: TValue | null
  defaultValue?: TValue
  onValueChange?: (
    value: TValue,
    eventDetails: CardGroupChangeEventDetails
  ) => void

  disabled?: boolean
  readOnly?: boolean
  required?: boolean
  name?: string
  form?: string
  inputRef?: React.Ref<HTMLInputElement>

  placement: CardPickerPlacement
  children: React.ReactNode
}
```

- Sans `defaultValue`, l’état initial ne contient aucune sélection et affiche `waitingContent`.
- En mode contrôlé, `null` représente explicitement l’absence de sélection.
- Une fois choisie, une radio ne peut pas être désélectionnée par une seconde activation : le comportement reste celui de Base UI Radio Group.
- Je conserverais `onValueChange`, pas un nouvel événement comme `onCardSelect`.

### Association des Hints

```ts
interface CardPickerHintItem<TValue extends React.Key> {
  value: TValue
  content: HintContent
}
```

La valeur correspond directement à celle du `Card.Selector`. `CardPicker.Hint` peut gérer lui-même les clés d’animation internes : je n’exposerais donc pas `waitingKey`.

Je rendrais obligatoire une correspondance exacte :

- chaque `Card.Selector.value` possède un Hint ;
- chaque valeur de Hint correspond à une Card ;
- aucune valeur n’est dupliquée.

`waitingContent` doit signifier « aucune sélection », pas servir de fallback silencieux lorsqu’une Card sélectionnée n’a pas de Hint.

### Sens des placements

- `block-start` (default) : Cards empilées au-dessus, Hint en dessous ;
- `block-end` : Hint au-dessus, Cards empilées en dessous ;
- `inline-start` : Cards au début de l’axe inline, Hint de l’autre côté ;
- `inline-end` : Hint au début de l’axe inline, Cards de l’autre côté

Les valeurs logiques donnent automatiquement le bon résultat en RTL.
