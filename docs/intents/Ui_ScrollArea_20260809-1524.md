# ScrollArea

Q&A avec ds-dev en mode pm-advice

## Q1

Composant ScrollArea
- wrapper de base-ui
- moteur css
- on style juste les barres : invisible en idle, apparaissent à l'enter de la zone en fade-in linear 150, disparaissent au leave en fade-out linear 150. barre verticale en width-6, barre horizontale en height-6, bg-foreground, les 2 rectangulaires
- pas de "gutter" visible pour les scrollbars
- corner ok mais juste pour éviter l'intersection

Possible ?

## A1

Oui, c’est entièrement possible avec Base UI 1.6 et un moteur CSS.

Base UI fournit exactement les primitives nécessaires :

- `data-hovering` sur chaque `Scrollbar` lorsque le pointeur est dans la zone.
- `data-orientation="vertical|horizontal"`.
- Des scrollbars positionnées en overlay, sans réserver de gutter dans le layout.
- Le masquage automatique d’un axe sans overflow.
- `Corner` pour retirer la zone d’intersection lorsque les deux axes débordent.
- Un `Viewport` natif, focusable lorsqu’il est scrollable et utilisable au clavier.

Le contrat visuel peut donc être :

- état initial : `opacity-0`, `pointer-events-none`;
- sur `data-hovering` : `opacity-100`, `pointer-events-auto`;
- transition : opacité, linéaire, 150 ms dans les deux sens;
- rail vertical transparent en `w-6`;
- rail horizontal transparent en `h-6`;
- `Thumb` en `bg-foreground`, pleine épaisseur, sans arrondi;
- `Corner` transparent, uniquement structurel.

Points à trancher avant la spec :

1. « `bg-foreground` sur les barres » doit probablement désigner les `Thumb`. L’appliquer aux `Scrollbar` colorerait toute la piste de 24 px et créerait précisément un gutter visible.
2. En comportement strictement hover-only, les barres ne se révéleront pas pendant un scroll clavier ou tactile. Base UI expose aussi `data-scrolling`; il faut décider si le scroll et le drag doivent maintenir leur visibilité.
3. Les barres de 24 px sont superposées au contenu. Sans gutter ni padding compensatoire, elles peuvent le recouvrir lorsqu’elles apparaissent.
4. Il faut choisir entre l’anatomie Base UI complète (`Root`, `Viewport`, `Content`, `Scrollbar`, `Thumb`, `Corner`) et un `ScrollArea` préassemblé qui rend automatiquement les deux axes.
5. Pour `prefers-reduced-motion`, je suggère de supprimer la transition tout en conservant les mêmes états de visibilité.

Aucun obstacle technique. Le seul vrai point contradictoire potentiel est `bg-foreground` sur la piste entière versus « pas de gutter visible ».

## A2

Oui, `m-px` sur les `Thumb` est compatible. Base UI tient compte de leurs marges dans ses calculs de taille et de déplacement.

Le résultat consolidé :

- API mono-composant : `<ScrollArea>{children}</ScrollArea>`.
- Deux axes préassemblés ; Base UI masque automatiquement celui sans overflow.
- Rails transparents superposés au contenu :
  - vertical : `w-6`;
  - horizontal : `h-6`.
- Thumbs rectangulaires, `bg-foreground`, avec `m-px`.
- `Corner` transparent, dimensionné sur l’intersection 24 × 24 px.
- Fade CSS linéaire de 150 ms à l’entrée et à la sortie.
- Transition supprimée avec `prefers-reduced-motion`.
- Aucun gutter ni padding compensatoire.

Pour le point 2 : imaginons que l’utilisateur saisisse un thumb puis sorte le pointeur du conteneur en continuant de le déplacer.

- Mode strict « hover » : le thumb disparaît dès le `leave`, même pendant le drag.
- Mode « interaction active » : il reste visible pendant le drag ou le scroll, puis disparaît 150 ms après la fin si le pointeur est dehors. Cela permet aussi de le voir lors d’un scroll clavier ou tactile.

Je recommande le second comportement : visible au survol ou pendant un scroll/drag actif. Il reste fidèle à « invisible en idle » tout en évitant qu’une barre disparaisse pendant son utilisation.

## Q3

Oui le second
Le comportement clavier est compatible avec tout ce qu'on a dit ?

## A3

Oui, entièrement compatible.

Au clavier :

- Le `Viewport` Base UI devient automatiquement focusable uniquement lorsqu’il contient un overflow.
- Les touches natives de défilement restent fonctionnelles : flèches, Page Up/Down, Home/End.
- Lorsqu’un déplacement se produit, Base UI applique `data-scrolling` sur la barre de l’axe concerné.
- Le thumb apparaît alors avec le fade-in linéaire de 150 ms.
- Après la fin du défilement, il disparaît avec le fade-out de 150 ms.
- Quand le viewport est seulement focusé mais reste idle, les thumbs demeurent invisibles.
- En réduction de mouvement, les mêmes changements sont immédiats.

Cela fonctionne aussi pour le tactile : pas de hover, mais `data-scrolling` révèle les thumbs pendant le geste.

Seule exigence d’accessibilité à conserver : ne pas supprimer l’indicateur de focus visible du `Viewport`. On peut garder l’outline natif du navigateur sans ajouter de style visuel Powercoach au conteneur. Les marges `m-px`, l’overlay et l’absence de gutter ne changent rien au comportement clavier.
