# AvatarMenu

Q&A avec ds-dev en mode pm-advice

## Q1

J'aimerais qu'on design un AvatarMenu basé sur NavigationMenu. ENgine CSS. Le portal et les items dans la liste doivent être repris depuis autocomplete. il faut aussi une orientation verticale par défaut, et toutes les animations qu'on a dans le premier exemple base-ui, notamment le no portal -> portal, et le portal to portal (quand on hover d'un avatar à un autre). Ca donnerait quoi ? quelles sont les autres décisions produit ?

## A1

Oui, c’est faisable avec Base UI 1.6. Je partirais sur un `AvatarMenu` spécialisé pour une colonne d’avatars, avec un unique Popup partagé qui se déplace et se transforme lorsqu’on survole un autre avatar.

### Anatomie proposée

```tsx
<AvatarMenu.Root orientation="vertical">
  <AvatarMenu.List>
    <AvatarMenu.Item value="yann">
      <AvatarMenu.Trigger aria-label="Ouvrir le menu de Yann">
        <Avatar.Image src="/yann.jpg" alt="" />
        <Avatar.Fallback>YA</Avatar.Fallback>
      </AvatarMenu.Trigger>

      <AvatarMenu.Content>
        <AvatarMenu.Link href="/athletes/yann">Profil</AvatarMenu.Link>
        <AvatarMenu.Link href="/athletes/yann/program">Programme</AvatarMenu.Link>
      </AvatarMenu.Content>
    </AvatarMenu.Item>

    {/* autres avatars */}
  </AvatarMenu.List>

  <AvatarMenu.Portal>
    <AvatarMenu.Positioner>
      <AvatarMenu.Popup>
        <AvatarMenu.Arrow />
        <AvatarMenu.Viewport />
      </AvatarMenu.Popup>
    </AvatarMenu.Positioner>
  </AvatarMenu.Portal>
</AvatarMenu.Root>
```

`AvatarMenu.Trigger` composerait publiquement les contrats d’`Avatar.Root` et de `NavigationMenu.Trigger` sur le même bouton DOM. Cela donne à la fois :

- la sémantique, le focus et les interactions de NavigationMenu ;
- le chrome, les tailles, l’image, le fallback et le Reveal d’Avatar ;
- aucun bouton imbriqué ;
- un `aria-label` natif obligatoire pour chaque avatar.

### Mouvement CSS

Le “portal-to-portal” Base UI est en réalité plus élégant : il n’y a qu’un seul Portal, Positioner et Popup. Seul le Content actif change.

Je reprendrais les séquences du premier exemple :

- Fermé → ouvert : Popup de `scale(.9) / opacity: 0` vers `scale(1) / opacity: 1`, depuis `--transform-origin`, sur 350 ms.
- Ouvert → fermé : même chemin inversé, avec sortie raccourcie à 150 ms.
- Avatar A → Avatar B :
  - déplacement vertical du Positioner vers le nouvel avatar ;
  - interpolation de `--popup-width` et `--popup-height` ;
  - déplacement vertical de l’Arrow ;
  - ancien et nouveau Content glissés et fondus dans le Viewport.
- Pour l’orientation verticale, les directions Base UI `up/down` remplacent les directions `left/right` du démo :
  - activation vers le haut : entrée depuis `translateY(-50%)`, sortie opposée ;
  - activation vers le bas : entrée depuis `translateY(50%)`, sortie opposée.
- `data-instant` supprime le déplacement lorsqu’une interpolation serait incorrecte.
- Toutes les durées deviennent nulles avec reduced motion.

Le Reveal propre à chaque Avatar peut rester : il donne le feedback local du trigger pendant que le Popup réalise le mouvement global.

### Point important sur Autocomplete

La réutilisation littérale n’est pas possible aujourd’hui :

- `Autocomplete.Portal` est seulement un wrapper contextuel sans apparence. Il ne peut pas porter le Portal de NavigationMenu.
- `Autocomplete.Item` dépend du Root Autocomplete, de sa valeur, de son highlight et de ses rôles d’option/commande. Il serait sémantiquement incorrect dans NavigationMenu.
- `Autocomplete.Popup` impose notamment la largeur de l’ancre ; avec un avatar carré, le menu ferait environ 36 px de large.

Ce qu’il faut réellement reprendre visuellement est donc le contrat de surface : géométrie carrée, border/background/foreground, hard shadow, densité des lignes, typographie, icônes et RevealAnimation.

Si “repris depuis Autocomplete” signifie une véritable source unique, il manque aujourd’hui une abstraction publique et sémantiquement neutre — par exemple une surface de popup et une surface de ligne — consommée ensuite par Autocomplete et AvatarMenu. Ce serait une révision liée d’Autocomplete, pas seulement la création d’AvatarMenu. Si une simple parité visuelle suffit, AvatarMenu peut avoir ses propres `Popup` et `Link`, composés avec `Text` et `RevealAnimation`, mais leur synchronisation future ne serait pas structurellement garantie.

### Décisions produit restantes

Les plus structurantes sont :

1. **Nature du contenu**  
   NavigationMenu convient à des liens de navigation. Si les lignes déclenchent surtout des commandes comme modifier, supprimer, se déconnecter ou sélectionner un athlète, `Menu` serait le meilleur socle accessible.

2. **Niveau de réutilisation d’Autocomplete**  
   Parité visuelle indépendante, ou extraction d’une fondation publique réellement partagée avec révision d’Autocomplete.

3. **API du Trigger**  
   `AvatarMenu.Trigger` possède directement `Avatar.Root`, comme dans l’exemple proposé, ou le consommateur compose manuellement `Avatar.Root` via `render`. La première option est plus naturelle pour un composant nommé AvatarMenu.

4. **Taille et densité**  
   Une seule prop `size` pilote-t-elle à la fois l’Avatar et les lignes ? Avatar possède sept tailles, Autocomplete seulement `xs/md/xl`, donc il faut définir un mapping ou découpler les deux.

5. **Dimensions du Popup**  
   Largeur intrinsèque, largeur fixe, `min-width`, ou largeur contrôlée par le consommateur. La largeur de l’avatar ne peut pas servir de référence comme dans Autocomplete.

6. **Placement par défaut**  
   Pour une rail verticale, je viserais `side="inline-end"` afin de respecter automatiquement LTR/RTL. Restent à décider `align`, l’écart de 1 px ou 10 px, les collisions et la présence de l’Arrow.

7. **Temporisation du hover**  
   Conserver les 50 ms Base UI pour `delay` et `closeDelay`, ouvrir immédiatement, ou utiliser des valeurs spécifiques. Cela influence fortement le passage rapide entre plusieurs avatars.

8. **État public**  
   Exposer seulement `value/onValueChange`, ou aussi l’usage non contrôlé avec `defaultValue`. Il faut également décider si `orientation="horizontal"` reste disponible malgré le défaut vertical.

9. **Fermeture après navigation**  
   `NavigationMenu.Link` a `closeOnClick=false` par défaut. Pour AvatarMenu, il faut choisir si un clic ferme systématiquement le popup, notamment avec un routeur client.

10. **Indicateur d’ouverture**  
    Le premier exemple anime aussi un caret sur 200 ms. Il faut décider s’il existe sur l’avatar, sous forme d’overlay/badge, ou si le Reveal de l’Avatar suffit.

Ma recommandation structurante serait : NavigationMenu vertical, Trigger possédant Avatar, un seul Portal partagé, mouvement vertical complet du premier exemple, et extraction d’une surface de liste commune si tu veux que “repris depuis Autocomplete” reste vrai dans le temps.

## A2

### Direction retenue

Je choisis une nouvelle famille publique et sémantiquement neutre : `PopupSurface`.

- `PopupSurface.Root` porte le chrome commun du popup : bordure, couleurs, hard shadow et animation CSS d’entrée/sortie.
- `PopupSurface.Item` porte exactement la ligne Autocomplete : taille, espacements, `Text`, slot `Icon` et `RevealAnimation`.
- Autocomplete est révisé pour consommer ces deux surfaces.
- AvatarMenu consomme les mêmes surfaces, en taille `md` fixe.
- Autocomplete conserve ses autres tailles.
- Les rôles restent possédés par les primitives Base UI : option pour Autocomplete, lien pour AvatarMenu.

Cela garantit une identité réelle, pas deux copies de styles susceptibles de diverger. L’ouverture/fermeture devient également identique : scale `0.9 → 1`, opacity `0 → 1`, 350 ms à l’entrée et 150 ms à la sortie. AvatarMenu ajoute uniquement les animations qui n’ont pas d’équivalent dans Autocomplete : déplacement du Positioner, morphing largeur/hauteur et transition verticale entre contenus.

Cela implique trois contrats liés :

- création de `PopupSurface` ;
- révision d’Autocomplete ;
- création d’AvatarMenu.

Avatar et Button n’ont pas besoin d’être révisés.

### AvatarMenu consolidé

```tsx
<AvatarMenu.Root defaultValue={null}>
  <AvatarMenu.List>
    <AvatarMenu.Item value="yann">
      <AvatarMenu.Trigger aria-label="Ouvrir la navigation de Yann">
        <Avatar.Image src="/yann.jpg" alt="" />
        <Avatar.Fallback>YA</Avatar.Fallback>
      </AvatarMenu.Trigger>

      <AvatarMenu.Content>
        <AvatarMenu.Link icon={<HomeIcon />} href="home">
          Home
        </AvatarMenu.Link>
        <AvatarMenu.Link icon={<DumbbellIcon />} href="programs">
          Programs
        </AvatarMenu.Link>
        <AvatarMenu.Link icon={<StarIcon />} href="reviews">
          Reviews
        </AvatarMenu.Link>
      </AvatarMenu.Content>
    </AvatarMenu.Item>
  </AvatarMenu.List>

  <AvatarMenu.Portal>
    <AvatarMenu.Positioner>
      <AvatarMenu.Indicator />
      <AvatarMenu.Popup>
        <AvatarMenu.Viewport />
      </AvatarMenu.Popup>
    </AvatarMenu.Positioner>
  </AvatarMenu.Portal>
</AvatarMenu.Root>
```

Contrat v1 :

- orientation verticale fixe, sans prop publique ;
- `delay` fixé à `0` ;
- `closeDelay` Base UI conservé, soit 50 ms par défaut ;
- Avatar et surfaces fixés en `md`, sans prop de taille ;
- `value`, `defaultValue` et `onValueChange` exposés avec les sémantiques Base UI ;
- `onOpenChangeComplete`, raisons d’événement et annulation Base UI préservés ;
- `closeOnClick=false` conservé sur Link ;
- `href` reste natif : AvatarMenu ne construit pas de routes depuis un `avatarId` ;
- Popup en `side="inline-end"` et `align="start"` — donc aligné en haut et compatible RTL ;
- largeur intrinsèque déterminée par le Link le plus long du Content actif, plafonnée par `--available-width` ;
- changement d’avatar : largeur et hauteur du Popup interpolées avec son déplacement vertical ;
- aucun Arrow ni caret.

### Indicator

`AvatarMenu.Indicator` est décoratif, `aria-hidden` et non interactif. Il suit l’avatar actif avec la même transition verticale de 350 ms que le Positioner.

Comme l’Avatar `md` possède déjà son propre chrome Button default, l’Indicator ne doit pas reprendre exactement la même boîte : il formera un cadre extérieur. La proposition la plus cohérente est une boîte `size-10` autour de l’Avatar `size-9`, soit environ 2 px visibles par côté, utilisant le chrome sémantique Button default. Le Reveal reste le signal principal d’ouverture ; l’Indicator sert surtout à relier visuellement l’avatar actif au Popup.

Il reste seulement deux micro-décisions produit :

- Le Link correspondant à la route active reste-t-il révélé en permanence via `active`, ou le Reveal est-il réservé au hover/focus ?
- Veut-on 1 px entre l’Indicator et le Popup, comme Autocomplete, ou un espace plus ample avec un pont de hover invisible ? Mon choix serait 1 px, cohérent avec la surface partagée et suffisant avec le `closeDelay` de 50 ms.

## A3

Oui. Je comprends “dynamique comme Tabs” ainsi : courbe fixe, cible géométrique dynamique et interruption réversible. Tabs utilise précisément `cubic-bezier(0.22, 1, 0.36, 1)`.

### Fusion Indicator–Popup

- `sideOffset` fixé à `0`.
- `align="start"` : le haut du Popup s’aligne sur le haut de l’Avatar.
- Indicator et Popup forment une seule silhouette.
- Aucune bordure ni ombre doublée à leur jointure.
- La bordure extérieure et le hard shadow décrivent la surface fusionnée.
- Aucun Arrow.
- L’Indicator entoure l’Avatar actif avec le chrome Button default, reste décoratif et n’intercepte jamais le pointeur.

### États actifs et Reveal

Il faut bien deux états distincts.

`AvatarMenu.Trigger` ajoute :

```ts
active?: boolean // défaut false
```

Son Reveal effectif devient :

```text
active || popupOpen || hovered || focusWithin
```

Ainsi :

- l’avatar courant peut rester révélé via `active` ;
- l’avatar dont le menu est ouvert reste révélé pendant le passage du pointeur vers le Popup ;
- hover et clavier continuent de fonctionner lorsque `active=false` ;
- `data-active` expose cet état au consommateur ;
- l’Indicator suit toujours le Trigger ouvert, pas nécessairement celui marqué `active`.

`AvatarMenu.Link` conserve le `active` natif de NavigationMenu.Link. Sa surface partagée se révèle lorsque :

```text
active || hovered || focusVisible
```

Autocomplete contrôle exactement la même `PopupSurface.Item` avec son état `highlighted`. On obtient donc le même Icon, le même Text, la même géométrie et la même RevealAnimation, avec des propriétaires sémantiques différents.

```tsx
<AvatarMenu.Trigger active={athlete.id === currentAthleteId}>
  <Avatar.Image src={athlete.image} alt="" />
  <Avatar.Fallback>{athlete.initials}</Avatar.Fallback>
</AvatarMenu.Trigger>

<AvatarMenu.Link
  active={route === 'programs'}
  href="programs"
  icon={<DumbbellIcon />}
>
  Programs
</AvatarMenu.Link>
```

### Mouvement

Je reprendrais le rythme de Tabs pour le changement d’avatar :

- Positioner : position sur 300 ms avec `cubic-bezier(0.22, 1, 0.36, 1)`.
- Indicator : position et éventuelle taille sur 300 ms avec la même courbe.
- Popup : largeur et hauteur sur 300 ms avec la même courbe.
- Content : translation verticale sur 300 ms avec cette courbe.
- Content : opacity sur 175 ms avec `ease`.
- Une interruption repart de la valeur CSS actuellement calculée, sans retour à l’ancien avatar ni saut de géométrie.
- Reduced motion supprime les translations et interpolations spatiales.

L’ouverture et la fermeture globale restent celles de la surface partagée avec Autocomplete : entrée scale/opacity, puis sortie raccourcie. L’Indicator n’a pas de fade indépendant : il entre et sort avec la silhouette fusionnée.

### Fermeture des Links

Je fixerais le défaut AvatarMenu à :

```ts
closeOnClick = true
```

C’est le comportement attendu pour un flyout React Router : sans rechargement de page, le popup ne doit pas rester ouvert après la navigation.

La prop reste exposée, donc le Manager peut explicitement passer `false` pour un cas particulier. Le `render` Base UI permet de composer un Link React Router à condition qu’il transmette bien les props et la ref.

Avec ça, je ne vois plus de décision produit bloquante pour l’intent.

## Q4

Vue que c'est vertical est ce que base-ui va nativement utiliser les fleche haut et bas du clavier ? car sur leur doc c'est horizontal et droite / gauche

## A4

Oui. Avec `orientation="vertical"`, Base UI 1.6 utilise nativement :

- `ArrowDown` pour passer à l’avatar suivant ;
- `ArrowUp` pour revenir à l’avatar précédent ;
- pas de boucle entre le dernier et le premier avatar.

La touche d’ouverture change aussi :

- en LTR : `ArrowRight` ouvre le popup du Trigger focalisé ;
- en RTL : `ArrowLeft` ;
- `Enter` et `Espace` restent disponibles via la sémantique du bouton.

Donc AvatarMenu fixera bien `orientation="vertical"` sur le Root Base UI, sans gestion clavier maison. Il faudra contractualiser et tester explicitement ces comportements, même si la démo principale Base UI est horizontale.
