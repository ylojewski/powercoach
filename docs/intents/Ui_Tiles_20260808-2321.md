# Tiles

Q&A avec ds-dev en mode pm-advice

## Q1

J'aimerais qu'on imagine ensemble un Composant Tiles
L'idée est de disposer de tuiles de différentes tailles et de différentes compositions graphiques séparées par de simple border avec token couleur border (border-border). Par "compositions graphiques" j'entends qu'une tuile peut-être dark ou non (si elle est dark, elle inverse le mode du parent, donc light -> dark et dark -> light), stripes ou non avec une stripesProps. Toute la Tile.Root peut-être également dark sur le même principe et toutes les Tile hérite. Les tuiles sont disposées selon un quadrillage définie via un ou des props selon ce que tu vas me proposer. Par exemple je veux pouvoir avoir un tile principale 3/4 de width puis une autre 1/4 de width sur une premiere ligne qui fait 3/4 de height, la seconde ligne fera 1/4 de height et aura 2 tiles 1 de 3/4 et une de 1/4. Je peux aussi préciser ce genre de "matrice" pour chaque breakpoint tailwind. Là ou ça devient intéressant c'est que Tiles doit être capable de tracker ses Tile et de les déplacer selon une animation CSS dès que le breakpoint change. COmment tu imagines tout ça

## A1

Oui, c’est faisable. Je verrais `Tiles` comme une grille responsive déclarative, avec deux parties publiques : `Tiles.Root` et `Tiles.Tile`.

### Anatomie proposée

- `Tiles.Root` possède la matrice responsive, les séparateurs, le thème hérité et le suivi des déplacements.
- `Tiles.Tile` possède une identité stable, son contenu, son éventuelle inversion de thème et sa couche `Stripes`.
- Aucun primitive interactif Base UI n’est nécessaire. Root et Tile rendent un `div` par défaut, avec un éventuel `render` selon les conventions Base UI pour produire un `section`, `article`, etc.
- Aucun rôle ARIA `grid` par défaut : il s’agit d’une composition visuelle, pas d’une grille interactive.

### Une matrice nommée

Je préfère une matrice centralisée sur Root à des `colSpan` dispersés sur chaque Tile. Elle rend immédiatement visible la composition complète et permet de détecter les collisions ou zones invalides.

```tsx
const layout = {
  base: [
    ['main'],
    ['aside'],
    ['secondary'],
    ['footer']
  ],

  lg: [
    ['main', 'main', 'main', 'aside'],
    ['main', 'main', 'main', 'aside'],
    ['main', 'main', 'main', 'aside'],
    ['secondary', 'secondary', 'secondary', 'footer']
  ]
} satisfies TilesLayouts
```

Puis :

```tsx
<Tiles.Root layout={layout} className="h-[36rem]">
  <Tiles.Tile area="main">Main content</Tiles.Tile>

  <Tiles.Tile area="aside" theme="inverse" stripesProps>
    Aside
  </Tiles.Tile>

  <Tiles.Tile
    area="secondary"
    stripesProps={{
      angle: '45deg',
      gap: '6px',
      width: '2px'
    }}
  >
    Secondary
  </Tiles.Tile>

  <Tiles.Tile area="footer">Footer</Tiles.Tile>
</Tiles.Root>
```

Chaque cellule représente une fraction égale. Ta matrice `4 × 4` produit donc naturellement les proportions `3/4 – 1/4` sur les deux axes. Une zone répétée doit former un rectangle continu.

Les breakpoints seraient mobiles-first :

```ts
type TilesBreakpoint = 'base' | 'sm' | 'md' | 'lg' | 'xl' | '2xl'
```

Un breakpoint absent hérite de la dernière matrice définie en dessous.

Point important : pour que `3/4` de hauteur ait une signification, Root doit recevoir une hauteur déterminée ou un `aspect-ratio`. Sinon, les lignes dépendront du contenu. Il reste à décider si cette géométrie appartient uniquement au consommateur via `className`, ou si Tiles expose aussi un prop dédié.

### Thème

Je n’appellerais pas le prop `dark`, puisque sa signification réelle est « inverser le thème effectif », et non « forcer le dark ».

```tsx
<Tiles.Root theme="inverse">
  <Tiles.Tile area="main" />
  <Tiles.Tile area="aside" theme="inverse" />
</Tiles.Root>
```

Contrat proposé :

- `theme="inherit"` : conserve le thème effectif du parent.
- `theme="inverse"` : light devient dark et dark devient light.
- Les Tiles héritent du thème effectif de Root.
- Une Tile `inverse` dans un Root `inverse` effectue une seconde inversion et revient donc au thème extérieur.

C’est techniquement cohérent avec l’inversion déjà réalisée par `RevealAnimation`, y compris lorsque la classe de thème d’un ancêtre change.

Pour `stripesProps`, je reprendrais le précédent établi par `Card.Visual` :

```ts
stripesProps?: boolean | TilesTileStripesProps
```

- `false` : aucune rayure.
- `true` : `Stripes` avec ses valeurs standard.
- objet : `Stripes` configuré.
- La couche compose le composant public `Stripes`; Tiles ne réimplémente pas son motif.

Le défaut — uni ou rayé — reste une décision produit.

### Bordures

Root devrait posséder tout le réseau de séparateurs :

- bordure extérieure de `1px` ;
- séparateurs internes uniques de `1px` ;
- couleur `border-border` ;
- aucune double bordure entre deux Tiles ;
- géométrie carrée.

Cela évite que deux Tiles adjacentes produisent une séparation de `2px`. Par défaut, les séparateurs suivent le thème effectif de Root. Il faut encore décider si une Tile inversée peut également inverser les séparateurs qui l’entourent ; ce serait nettement plus complexe car chaque séparation est partagée par deux surfaces.

### Animation responsive

Une simple transition CSS sur `grid-area` ne produira pas le déplacement attendu : le navigateur change la zone de grille de façon discrète.

Le contrat viable serait :

1. Root identifie chaque Tile grâce à son `area`.
2. Au changement de breakpoint, la nouvelle matrice devient la mise en page réelle.
3. Chaque Tile présente dans les deux matrices passe visuellement de son ancien rectangle au nouveau avec une transition CSS de transformation.
4. Les éléments ne sont pas remontés : contenu, état local et focus sont conservés.
5. Un redimensionnement rapide repart de la position visuelle courante.
6. Le premier rendu n’est pas animé.
7. `prefers-reduced-motion: reduce` applique immédiatement la nouvelle matrice.

Le JavaScript ne ferait ici que suivre les rectangles et le breakpoint ; le moteur de mouvement resterait bien CSS.

J’exposerais seulement quelques crochets publics utiles :

- `data-layout="lg"` sur Root ;
- `data-animating` pendant une transition ;
- `data-area="main"` et éventuellement `data-moving` sur Tile ;
- `--tiles-motion-duration` ;
- `--tiles-motion-easing`.

Le point à trancher est le redimensionnement. Trois contrats sont possibles :

- déplacement uniquement, avec changement de taille immédiat ;
- déplacement et mise à l’échelle, plus fluide mais le texte se déforme temporairement ;
- animation complète des dimensions sans déformation du contenu, plus sophistiquée et avec des règles de clipping/reflow à définir.

Enfin, l’ordre DOM doit rester stable et représenter l’ordre logique de lecture et de tabulation. Les matrices peuvent déplacer visuellement les Tiles, mais ne devraient pas créer un ordre visuel contradictoire pour du contenu interactif.

Les décisions produit encore ouvertes sont donc : taille animée ou non, défaut de `stripesProps`, propriété de la hauteur/aspect-ratio, thème des séparateurs autour d’une Tile inversée, durée/easing, et comportement d’une Tile absente d’une matrice à un breakpoint donné.

## A2

Oui, c’est possible, et le nesting s’accorde très bien avec les container queries CSS.

Le contrat naturel serait :

- Un `Tiles.Root` sans ancêtre `Tiles.Tile` utilise le viewport.
- Un `Tiles.Root` placé dans une `Tiles.Tile` utilise automatiquement la largeur de la Tile parente.
- Chaque Tile devient donc un conteneur responsive potentiel.
- Chaque Root ne suit et n’anime que ses propres Tiles directes.

```tsx
<Tiles.Root layout={outerLayout}>
  <Tiles.Tile area="main">
    <Tiles.Root layout={innerLayout}>
      <Tiles.Tile area="summary">Summary</Tiles.Tile>
      <Tiles.Tile area="details" stripesProps={{ gap: '6px' }}>
        Details
      </Tiles.Tile>
    </Tiles.Root>
  </Tiles.Tile>

  <Tiles.Tile area="aside">Aside</Tiles.Tile>
</Tiles.Root>
```

Ici, `outerLayout` réagit au navigateur. `innerLayout` réagit à la largeur disponible dans `main`, même si le navigateur reste en plein écran.

Tailwind 4 prend nativement en charge les container queries et les conteneurs nommés imbriqués. Il distingue néanmoins les breakpoints viewport (`sm` = `40rem`) des tailles de container (`@sm` = `24rem`) : il faudra choisir quelle échelle les matrices imbriquées utilisent. [Documentation Tailwind](https://tailwindcss.com/docs/responsive-design)

### Animation imbriquée

Le scénario est faisable avec le moteur CSS confirmé :

1. La matrice extérieure change.
2. La Tile parente reçoit immédiatement sa nouvelle boîte de layout.
3. Sa transformation CSS la fait visuellement passer de son ancienne position et taille à la nouvelle.
4. Le `Tiles.Root` intérieur détecte la nouvelle largeur de layout de sa Tile parente.
5. Si cette largeur traverse un breakpoint, sa propre matrice change et ses Tiles commencent leur mouvement local.

Les transformations se composent : la grille intérieure se déplace et se met à l’échelle dans une Tile elle-même en mouvement et en mise à l’échelle.

Une nuance importante : les container queries examinent la taille de layout, pas la taille visuelle produite par `transform: scale()`. Le breakpoint intérieur bascule donc dès que la Tile reçoit sa géométrie finale, et non au moment où sa taille animée franchit visuellement le seuil. C’est cohérent et déterministe, mais les animations extérieure et intérieure démarrent alors ensemble.

Si tu souhaites au contraire que l’intérieur attende la fin du mouvement extérieur, il faudrait définir une animation en deux phases.

### Décisions désormais fixées

- La matrice reste autoritaire : le contenu ne peut pas agrandir une ligne ou une colonne et casser les proportions.
- Le mouvement anime position et mise à l’échelle.
- `stripesProps={undefined}` signifie aucune Stripes.
- Root prend la taille donnée par le consommateur ; la matrice la répartit.
- Le consommateur décide du traitement de l’overflow.
- Le nesting peut être récursif à plusieurs niveaux.
- Thème et inversion continuent naturellement à s’hériter à travers les niveaux.

Pour préserver les proportions, les tracks devront rester indépendants du contenu. Si un contenu ne tient pas, il faudra donc le clipper, le faire défiler ou le laisser déborder selon un contrat explicite.

### Point subtil sur le ratio animé

Au repos, chaque Tile respecte exactement le rectangle défini par sa matrice.

Pendant une transition entre deux matrices dont les rectangles ont des proportions différentes, la mise à l’échelle interpole nécessairement entre les deux ratios. Sa boîte de layout respecte déjà la matrice d’arrivée, mais son apparence transformée possède temporairement un ratio intermédiaire.

Si « toujours respecter le ratio » inclut chaque image de l’animation, cela entre en conflit avec « déplacement et mise à l’échelle » lorsque les ratios de départ et d’arrivée diffèrent. Il faudrait alors choisir entre cropping, espace vide ou changement de ratio instantané.

### Décisions restant à fixer

- Les Tiles imbriquées utilisent-elles les seuils viewport Tailwind (`sm = 40rem`) ou l’échelle container Tailwind (`@sm = 24rem`) ?
- Les animations extérieure et intérieure démarrent-elles simultanément ou successivement ?
- Le ratio doit-il être exact uniquement aux états de repos, ou également à chaque image de l’animation ?
- Quand un contenu dépasse sa Tile : clipping, scroll ou overflow visible ?
- Un Root imbriqué dessine-t-il sa propre bordure extérieure, au risque de doubler celle de la Tile parente, ou seulement ses séparateurs internes ?
- Quelle durée et quel easing pour les déplacements ?
- Que devient une Tile absente de la matrice active : cachée, interdite ou placée automatiquement ?

## A3

Tu as raison : dans ton intention, il ne faut pas animer `transform: scale()`, mais la géométrie réelle de la Tile.

J’avais évoqué `scale` parce que c’est la technique habituelle de type FLIP : elle évite les recalculs de layout, mais elle agrandit temporairement les pixels, le texte et tout le contenu. Ce n’est pas ce que tu décris.

### Contrat de mouvement corrigé

Lors d’un changement de matrice, chaque Tile interpole simultanément :

- sa position horizontale ;
- sa position verticale ;
- sa largeur ;
- sa hauteur.

La Tile possède donc réellement une largeur et une hauteur intermédiaires. Son contenu se recompose pendant les `200ms` au lieu d’être étiré visuellement.

Le mouvement reprend la courbe dynamique de Tabs :

```css
transition:
  left 200ms cubic-bezier(0.22, 1, 0.36, 1),
  top 200ms cubic-bezier(0.22, 1, 0.36, 1),
  width 200ms cubic-bezier(0.22, 1, 0.36, 1),
  height 200ms cubic-bezier(0.22, 1, 0.36, 1);
```

Comme pour l’Indicator de [Tabs.md](/Users/yann/Projects/powercoach/packages/ui/docs/design-system/components/Tabs.md:991), une interruption repart des valeurs calculées courantes sans revenir à l’ancien rectangle.

Au repos, la géométrie respecte exactement la matrice. Pendant les `200ms`, elle interpole naturellement entre les deux rectangles valides.

### Nesting simplifié

Le modèle le plus simple consiste à faire réagir chaque `Tiles.Root` à sa propre largeur disponible :

- un Root principal occupe généralement la largeur de la page et suit donc indirectement le navigateur ;
- un Root imbriqué occupe la largeur de sa Tile parente et suit donc automatiquement cette Tile ;
- tous utilisent l’échelle native des container breakpoints Tailwind ;
- aucune distinction publique `viewport`/`container` n’est nécessaire.

Lorsque la largeur réelle de la Tile parente s’anime, le Root imbriqué voit cette largeur évoluer. S’il traverse un breakpoint, sa matrice change et ses propres Tiles commencent immédiatement leur transition. Les animations des deux niveaux peuvent donc se chevaucher, comme demandé.

### Contrat désormais établi

- Moteur : CSS.
- Position et dimensions réelles animées ; aucun `scale`.
- Durée : `200ms`.
- Easing : `cubic-bezier(0.22, 1, 0.36, 1)`.
- Reflow imbriqué simultané.
- Reduced motion : géométrie finale immédiate.
- `stripesProps={undefined}` : aucune rayure.
- Root prend la taille donnée par le consommateur ; la matrice la répartit.
- Le consommateur décide du traitement de l’overflow.
- Chaque aire doit correspondre exactement à une Tile.
- Chaque Tile doit apparaître dans toutes les matrices.
- Aucun placement automatique ou aire manquante.
- Root possède le réseau de séparateurs.
- Un Root imbriqué ne redessine jamais la bordure extérieure déjà possédée par sa Tile parente ; il ne dessine que ses séparateurs internes.
- Les séparateurs restent donc toujours simples, jamais doublés.

Le seul détail encore ouvert est la couleur d’une séparation partagée entre une Tile normale et une Tile `theme="inverse"` : elle doit être possédée soit par le thème de Root, soit par l’une des deux Tiles. Le thème de Root donnerait le résultat le plus stable.
